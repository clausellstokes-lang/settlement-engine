## 2 · EVERY ASSUMPTION THAT BREAKS (the adapter's whole job)

1. **Two distinct combatant ids — the same save id cannot fight itself.** `hostilePairFor` returns false for `aId === bId` (:539); `detectCollisions` iterates `i<j` over distinct keys (:538-540); the field fork key `battle:<a>:<b>:<tick>` and the news id `wizard_news.<tick>.field_battle.<a>.<b>` (:601) degenerate on equal ids. **Fix: mint typed party ids** (`rising:<T>` / `loyal:<T>`), which also gives a distinct rng stream. Minor flag: the fork key concatenates raw ids with `:` un-length-prefixed (`armyTransit.js:482`) — use colon-free suffixes or the `stableParts` idiom (`armyTransitKernel.js:104-106`) in any NEW key.
2. **The one-army law: `worldState.deployments[saveId]` is one record per settlement** ("A settlement fields EXACTLY ONE army", `warDeployment.js:4`). An irregular force written there would collide with the settlement's own army and be swept into step-3 siege collection (:453-456, keyed by `dep.targetId`). **Never write deployments** — the convergence isolated-ledger ruling (:42-50) is the constitutional precedent, and it protected "the 6 role:'siege' readers" by construction.
3. **No transit row, ever.** The transit ledger is keyed by settlement id, derived FROM deployments (`kernel :653`), `planMarch` needs a route (origin→dest hops; same-node is meaningless), and a RETREAT's `destId === originId` already has special-cased semantics (CS-A4, :684-699). Intra-settlement contests have no march. D10 borrows the ledger IDIOM only.
4. **`capacityFor(id)` resolves snapshot items** — `buildCapacityLookup` returns the zero envelope for an unknown id (`warCapacityReads.js:178-182`). The adapter supplies its own closures: typed rising id → the NAME-4-derived envelope; typed loyal id / contest id → garrison + (1−participation)·levy per D10. Same for `effectiveStrengthFor` (the contest-window row's `currentEffectiveStrength`).
5. **Siege-of-self semantics — three specific mis-applications:**
