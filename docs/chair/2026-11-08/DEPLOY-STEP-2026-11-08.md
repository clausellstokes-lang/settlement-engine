5. **Vercel:** Project → Settings → Environment Variables → Production: `VITE_ENGINE_REMOTE=true` (and `VITE_ENGINE_GENERATE_URL` / `VITE_ENGINE_ADVANCE_URL` if the design's "What the owner does" names them for your project). The value is baked at build time.
6. **Redeploy the client** from the merged commit (the CI-gated deploy job, or a Vercel redeploy of that commit). The shipped `dist/` now has no generator.
7. **Post-deploy verification:** `npm run ops:post-deploy` with the production health and database settings (`docs/ops/POST_DEPLOY_VERIFICATION_RUNBOOK.md`) — it produces the release receipt. The chair's one addition, recommended: a timed call through `engine-generate` for one seed per tier, so the receipt carries a latency number for the first server-side generations.
8. **THE THREE-MINUTE SMOKE — in a private browser window on the production site, before you tell anyone (NEW 2026-11-10).** No test in the repository or in CI can reach your production functions, so this is the first time a browser generates through the server. Four acts, in order:
   - **(a) As a visitor, signed out: generate a town.** It must appear. This proves the shipped client has no generator of its own and that `engine-generate` answers a stranger from your production address (the visitor path is metered by IP, §1.3). It is exactly the act that failed in the chair's rehearsal before REMOTE-PATH; if the page says "Generation failed" here, the flag goes OFF (§3) without further diagnosis.
   - **(b) Sign in, generate again, and save the town.** This proves the account path, and the save now carries the composed text (210).
   - **(c) Share it: press `Unlisted link`, then `Copy party link`, and open that address in a second private window.** The page must print the town's written blocks and no DM content (208 and 210 together). The bar that replaces the button carries the link from then on; it changes only if you press `Rotate link`.
   - **(d) Back in your account, open the saved town's NPCs or History tab and press `↺ Reroll`.** This proves the third server path (section regeneration).
   - **(e) The heaviest thing the wizard can ask for: in Advanced mode at Metropolis, press Force all on the institutions and generate.** It is the browser's own version of step 4a's heavy half, which already passed if you are here; the town must appear (it is a very large one: 247 institutions). **If it fails while (a) to (d) pass, the flag goes OFF (§3)** and the chair is told: every other size works without the flag exactly as it does today, and a button the wizard offers must not fail with advice that cannot help.

   **If (a) fails,** open the browser's developer tools → Network → the `engine-generate` request and read its status. **409** = the functions were not deployed from the merged commit (step 4). **404**, or a failure with no status and a CORS message in the console = the function is not on the project (step 3), or the site's address is not one the functions accept (`supabase/functions/_shared/cors.ts` lists them; add yours to the project's `ALLOWED_ORIGINS` secret). **429** = the dials (§1.3). Any **5xx** = read the function's log (step 9). **If it is not cured within a few minutes, turn the flag OFF (§3):** the redeployed client generates in the browser again, exactly as production does today, and nothing saved is touched. The migrations stay applied either way; they do not depend on the flag.
9. **Watch:** Admin → Analytics' first line "Engine generations (today / this month)" (needs 204 applied); the Supabase dashboard's Edge Functions → engine-generate → Logs for invocations and errors; the 429 rate (the dials) and the 409 rate (a stale client meeting a new engine — the stale-deploy guard reloads such a tab).

## 3. Turning it OFF again

Set `VITE_ENGINE_REMOTE` back off in Vercel and redeploy: the client build carries the generator again and runs it in the worker; the functions may stay deployed, unused.
