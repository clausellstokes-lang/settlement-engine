# (D) WHAT IT WOULD COST TO LAND

**THE GATE.** Two mechanisms exist. (1) A GENERATION LAW (`densityCreateBoundary.js :: GENERATION_LAWS`: density, livingContent, seat, fortune): a dial and a config key (`_xLawVersion`) that `birthConfig` mints on every classified birth. It is lit by flipping the dial, and it writes a byte into every new record. (2) THE STAMP FLOOR `settlement.schema.js :: bornAtOrAfter(record, '<literal>')`, which reads the `generatorVersion` that `assembleSettlement` already stamps. Its precedent sits in the same file: `genesis.js :: FIELD_RITE_SINCE = '0.10.0'`. This cure needs (2): a NEW literal `NEEDS_SINCE = '0.10.0'`, and no new law, dial or config key. A law would buy nothing here. Genesis runs on the finished record, never in the pipeline, so a stamp the record already carries is enough. A law would also move every born record's config by one key, against 0 records moved under (2) (C).

**DOES IT NEED A VERSION BUMP? No, on one condition (PLAUSIBLE: I could not measure the deploys).** The tree stamps 0.10.0 and master stamps 0.9.0. A town saved in production is 0.9.0 (or has no stamp and loads as `LEGACY_GENERATOR_VERSION = '0.9.0'`), so it keeps its draw. The condition is that no saved town anywhere already carries 0.10.0. Genesis re-runs at EVERY VIEW of an unlit town, so a 0.10.0 town saved before landing (from a preview or a staging deploy of this tree, if one exists) WOULD re-deal its Traditions tab on reopen: about a quarter of them (444 of 1,800 on C+V). Its shared page would change at its next save. A lit 0.10.0 town keeps its stored mirror. The earlier seat's caution (R9: "bump GENERATOR_VERSION with it") holds only if such 0.10.0 saves exist. If any do, the floor must be a stamp no saved town carries: bump to 0.10.1 and set the floor to '0.10.1'. FIELD_RITE_SINCE would stay at '0.10.0'.

**AN OLDER SAVED TOWN RE-OPENED: BYTE FOR BYTE (CONFIRMED, `scripts/check-D.mjs`).** I re-stamped every one of the 1,800 births '0.9.0', and then stripped the stamp. Base and candidate drew, showed and shared identical JSON on 1,800 of 1,800 towns, both ways. The re-stamp to '0.10.0' differs on exactly the 444 towns. A lit town's stored recs are never re-derived.
