### 1.2 The read paths, enumerated by execution (the catalog at f07db8760)

Every `security definer` function `anon` can execute whose body reads `settlements.data`, `ai_data`,
`campaign_state` or `gallery_member_overrides`: **four** — `get_gallery_dossier`, `get_unlisted_dossier`,
`get_gallery_map`, `publish_settlement` (owner-only: it checks `auth.uid()`); plus `import_gallery_dossier`
(`authenticated` only). All four public dossier reads are restated by 211 and call `_gallery_veil`.
`settlements` RLS is owner-only (001, 024, 059, 179): no policy gives `anon` or another user a row, so the
stored `$veil` (deltas and the frozen copy) is unreachable by a direct table read.

The listing and tile reads (`list_gallery_dossiers`, `list_curated_dossiers`, `list_featured_dossiers`,
`list_gallery_more_by_creator`, through `_gallery_public_tile_rows`) never send `data`; search reads only the
title, the description and the tags. They DO send nine coarse columns derived from the LIVE `s.data` (finding
C1). `_gallery_public_tile_rows` itself is not executable by `anon` or `authenticated`.

Privileges after 211: all 43 `_gallery_veil*` helpers are executable by neither `anon` nor `authenticated`
(the closing `DO` block revokes them from `public, anon, authenticated`, which also undoes Supabase's default
grant on new functions). Every restated read pins `search_path = public, pg_temp`. The helpers carry no
`search_path` of their own; they are called only from the pinned definers, qualify every call `public.`, and
cannot be called by a reader, so they inherit a safe path. Grants on the four reads are restated as they stood.
`_gallery_apply_member_overrides`, `_gallery_dm_full_json` and `_gallery_npc_key` stay executable by `anon` (as
before 211): they are invoker, pure functions of their arguments, and give a caller nothing it did not pass in.

### 1.3 Fail-open audit of the reads (read, and probed)

- `coalesce(vl.v -> 'body', proj.d)`: the unveiled projection is served only when `_gallery_veil` returns no
  `body` key, which happens only when `_gallery_veil_resolve` returns NULL, i.e. `$veil` is not a JSON object and
  the read is not the party link. That is exactly the client's `readShareVeil(...).marked === false` (the client
  tests `isRec(stored)`), so the server never serves unveiled what the client would veil. A `body` that comes
  out SQL NULL (a strict `jsonb_set` fed NULL) becomes JSON `null`, not a fallback: fail-closed.
- Snapshot mode requires `$veil` to be an object, so every frozen copy is served through the veil.
- A frozen copy past `_gallery_veil_copy_bound()` is refused (no row) on the gallery read, the import and the
  map; it is never replaced by the live row.

### 1.4 Findings from the cold pass

**C1 — LOW-MEDIUM (live town out of a frozen share, outside the four reads' `data`).** A share in snapshot mode
serves the frozen copy as `data`, but `get_gallery_dossier` returns beside it, and every gallery tile and the
og-image card show, nine columns computed from the LIVE row by `_gallery_public_tile_rows`: `population`,
`terrain`, `government_type`, `magic_level`, `stability`, `primary_resource`, `threat_level` (and `name`, `tier`).
- Where: `_gallery_public_tile_rows` (last restated by 147/148), selected by `get_gallery_dossier`
  (`211_server_side_share_veil.sql:1200-1206`), `list_gallery_dossiers`, `list_curated_dossiers`,
  `list_featured_dossiers`, `list_gallery_more_by_creator`; `supabase/functions/og-image/index.ts:219-223`.
- Reproduce (probe `live.mjs`, PGlite 001..211): live row `{population: 9999, powerStructure: {government:
  'LIVE_COUP_JUNTA', stability: 'LIVE_COLLAPSING'}, threatProfile: {level: 'LIVE_DIRE'}}`, `$veil = {mode:
  'snapshot', snapshot: {population: 100, government 'FROZEN_COUNCIL', ...}}`. `get_gallery_dossier` returns
  `data.population = 100` and, beside it, `population = 9999, government_type = LIVE_COUP_JUNTA, stability =
  LIVE_COLLAPSING, threat_level = LIVE_DIRE`; `list_gallery_dossiers` shows the same live four on the tile.
- How bad: anyone (anon) reads the live town's coarse state after the freeze — a coup, a collapse, a new threat
  level, a population change the DM froze the page to keep from the table. Not DM truth the veil hides (these
  facts are public on a live page), and 210 sent far more (the whole live row). Pre-existing, not opened by 211.
- Cure: in snapshot mode, compute the tile columns from the frozen copy (or stamp them at freeze), or the owner
  rules the coarse columns live by design and the hand-back records it.

**C2 — NOTE (by design, recorded).** The party link of a snapshot share draws the LIVE town (208's design; the
served marker drops `at`, R5). Probe: `get_unlisted_dossier` of the same share returns `dossier.name = LIVE,
population 9999`. Safe only because the unlisted slug is a separate secret the gallery read never returns. A
share whose mode word is `snapshot` with no copy stored (an older client's write) is likewise served live under
`mode: snapshot`, without `at` (probe: `snapshot-without-copy: data.name LIVE`).

**C3 — NOTE.** `get_gallery_map` passes `link = false`: a member town that is unmarked (never exported through
the share panel) is served sanitised but WITHOUT the default veil, while the same town on its party link takes
the default veil (R4). This is the chair's ruling 1 ("each member through its own listing's veil") and matches
the client's map page; recorded so the owner knows the map page is the one public read where an unmarked town's
default-hidden groupings (plot hooks, criminal services, ...) still travel.

**C4 — NOTE (deploy).** The rollback restores 210 exactly, and so reopens the leak 211 closes (the gallery read
again sends the stored `$veil` — deltas and frozen copy — and every veiled string). A rollback is an un-veiling,
not a neutral undo; the owner should read it that way.
