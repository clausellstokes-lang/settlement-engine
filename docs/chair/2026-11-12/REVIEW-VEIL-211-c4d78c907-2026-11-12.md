### R3 — A storable number past about 2.5e130748 in a person's name or id makes every read raise at 211 (210 serves). This includes unmarked listings and the whole map. CONFIRMED. New in 211.

- **What breaks.** The gallery page, the party link, the import and the **entire map** that holds the town ("value overflows numeric format"). Every member of the map is lost, not only this one. It happens on an **unmarked** listing too, which 211's header promises to serve "exactly as before", because `_gallery_veil` builds its people list (line 916) before it tests whether the share is marked.
- **Cause.**
  - `_gallery_veil_num_zero` (line 151) decides "does JS read this as zero" by computing `abs(x) * 2^1075 <= 1`.
  - jsonb stores any numeric up to 10^131072. For |x| ≥ ~2.47e130748 the product overflows numeric's own range.
  - The call chain is `_gallery_veil_truthy` (line 167) ← `_gallery_veil_npc_id` ← the people list, for every person in `npcs[]` and every faction roster.
  - `_gallery_veil_numstr` (line 212) has the same multiplication.
  - The F3 cure removed the float casts, but not this.
- **Rows** (`rv/mk.sql`, `rv.reads`, `rv.mapread`):
  ```
  c210 ov={}                    {"npcs":[{"name":"A","id":1e131071}]}   ok | ok | ok | map ok
  c211 ov={}                    {"npcs":[{"name":"A","id":1e131071}]}   RAISE: value overflows numeric format (gallery | link | import | map)
  c211 ov={"$veil":{…}}         {"powerStructure":{"factions":[{"name":"F","members":[{"name":2.5e130748}]}]}}   RAISE (all four)
  ```
  The same number in a frozen copy (gallery) or in the narration (gallery and link) raises too (`rv/pdfix.mjs`: `overflowcopy`, `overflownarr`). The id differential raised on all 176 of its 23,684 cards holding `1e131071`, and on nothing else.
- **Who can store it.** Only the owner, in their own row, by a raw PostgREST write: 8 characters in the request (`1e131071`), stored and printed as 131,080 digits. `JSON.stringify` cannot write it. 1e130747 does not raise.
- **Severity.** Low for confidentiality (none). For availability: the owner can break their own listing, link and every map holding the town, with a row that works at 210. This is the class the brief and the first review name NOT CLEAR, and the claim at `cdc6225d0` ("nothing storable makes a read raise") is false.

### R4 — With Reveal DM on, a document nested about 550 deep that holds any key matching /hook/ makes the gallery read raise at 211 (210 serves to 900+). CONFIRMED. New in 211.

- **Cause.** `_gallery_veil_drop_hooks` (line 508) is recursive plpgsql. It runs for the `tab:plot_hooks` grouping (a default) whenever the text prefilter (line 761) sees a `…hook…": ` key. Under Reveal DM, `_gallery_dm_full_json` keeps deep nesting that the sanitiser drops, so 210's gallery read serves it and 211's walk exhausts the stack.
- **Row** (`rv/depth.mjs`): `{"name":"T","npcs":[{"name":"A"}],"deep":<N nested objects or arrays ending in {"theHook":"x"}>,"lore":{"aHook":"z"}}`, `gallery_share_dm = true`, marked `$veil` (gallery / link):
  ```
  c210 obj 550..900 ok / ok        c211 obj 500 ok / ok   c211 obj 550 RAISE: stack depth limit exceeded / ok
  c210 arr 550..900 ok / ok        c211 arr 500 ok / ok   c211 arr 550 RAISE: stack depth limit exceeded / ok
  CONTEXT: PL/pgSQL function _gallery_veil_drop_hooks(jsonb) line 3 at RETURN   (the stored row is 1,910 bytes)
  ```
- **Who.** The owner. `JSON.stringify` can write this shape, so a client save could store it if the DM's own data (custom content, a pasted or imported JSON) were that deep. It breaks the owner's own gallery page under Reveal DM. The link is unaffected because the sanitiser drops the subtree there. The threshold depends on the server's `max_stack_depth` (default 2 MB here).
- **Severity.** Low, by reach. It is the same NOT-CLEAR class as R3.
