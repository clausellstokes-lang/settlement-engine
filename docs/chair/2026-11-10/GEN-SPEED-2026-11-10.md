## Cure 1 — `src/domain/institutions/defenseInstitutionBuckets.js :: partitionDefenseInstitutions`

**What repeated.** `matches` called `nativeSemanticName(inst).toLowerCase()` once PER KEYWORD per
bucket: up to 34 readings of one name per call. The function is reached for every candidate line
of every hook draw (`factsOf(record).guardPresence` → `defenceOf` → `defenseFactsOf` →
`standingDefenseForces`). The cure reads and lowercases each name ONCE, before the buckets, into
`lowered[i]`; every bucket tests `lowered[i]` with the same `includes` over the same keywords;
members are kept by `list.filter((_, i) => …)`, so by identity and in roster order.

**Why the remembered answer cannot differ from the recomputed one.** The remembered value lives
for one synchronous call. Between the reading and the last bucket's test, the only code that runs
is `Array.prototype.some` and `String.prototype.includes` on the reading itself and the frozen
keyword table; nothing can write the member. `nativeSemanticName` is a pure read of the member's
own fields (`isCustom`, `custom`, `source`, `customDefinitionId`, `customDefinitionCategory`,
`name`). So each keyword is tested against the very string it was tested against before. The
module's types are unchanged (`unknown` members); `typecheck:domain:strict` stays at its ceiling.

The pin's second test fixes the partition's answer at the base (every bucket, vocabulary order,
members by identity, a custom row excluded, a string member classified, a null skipped) and is
green before and after.

## Cure 2 — `src/generators/npc/rosterFrame.js :: rosterFramer` (new), used by `npcGenerator.js :: generateCrimeLevel`

**What repeated.** The 25% branch (STYLE-2 SW-7: the held key is the FRAME, every roster name
masked) built `heldFrames = new Set([...held].map(frameOf))` for every person who took the branch,
re-framing the whole held set: persons × held × names `split/join` steps, cubic in the roster. The
caller (`narrativeGenerator.js :: enrichNpcCoherence` → `heldByOthers`) hands a NEW held set to
every person, so nothing could be remembered on the set.

**The cure.** `rosterFramer(rosterNames)` returns the framer for that roster. It keeps ONE
module-level slot `{ key, frames }`; `key` is `JSON.stringify(rosterNames)` computed at EVERY call
from the ordered list as it is at that call; a different key replaces the slot. Within the slot a
text's frame is remembered under the text's own string value. The masking that fills the slot is
the SAME sequential longest-first `split(name).join('@')` over the same list in the same order,
then `trim()` — not an alternation regex (the brief's prohibition, honoured: the two differ where
names overlap). A list holding anything but a string is never remembered (its JSON could not stand
for what `split` coerces); it is masked afresh, as before. The import rides the existing import
line of `npcGenerator.js` (its `max-lines` ceiling, and no cited line moves).

**Why the remembered answer cannot differ from the recomputed one.** A frame is a pure function
of exactly two values: the ordered name list and the text. Both are the key, by CONTENT. What
could change between two reads: (a) a person renamed, added or removed between two calls — the
list's JSON changes, so the slot is replaced; (b) the same names in another order (equal-length
names, whose relative order the stable sort takes from the roster) — the JSON changes, the slot is
replaced, so order-dependent overlaps are framed afresh; (c) a record or array written by a later
step — nothing is keyed by identity, so no write can make a remembered frame stale; (d) the
framer captured by `heldKey` while another roster replaces the slot — the closure holds its OWN
`frames` map, which belongs to its own key, so it can never read another roster's frames. The
second pin runs a roster, then a different roster, then the first roster again as FRESH records,
and gets byte-identical answers.

Memory: one slot, the last roster's frames (a few hundred texts), replaced by the next roster.

## Cure 3 — C′: `src/generators/people/representatives.js :: spareHookLine` (the chair's ruling (a))

**The brief's C, measured and withdrawn.** C was "one reading of each fact per `drawDeclared`
call". Counted on the force-all case with an instrumented copy of the bundle (scratch, not the
repo): across 10,893 `drawDeclared` calls, `guardPresence` was read 413 times and NEVER twice
within one call; counting every getter, 175 of 844 reads repeated within a call, only 3 of them
the expensive `defence`. A per-call memo would have removed about 3 of 459 partitions. The
re-profile showed why: the quarter of the CPU under `resolveDeclared` is `spareHookLine`'s walk,
whose `facts` thunk built a NEW `factsOf` for every ROW (one-row pools); across one walk 350 of
its 406 `guardPresence` reads repeated. Written to the chair before any build; ruled (a): build C′,
with three conditions, each met below.

**The cure.** `spareHookLine` builds ONE `factsOf({ institutions, tier }, { waterKind })` and reads
it through `rememberedFacts` (a module-private function beside it): a frozen object with one lazy
getter per own key of the facts object, each reading the live getter at most once. It is created
inside the call and dropped when the call returns (condition 1: no module state; `factsOf` itself
still remembers nothing). A function-valued fact (`hasInstitution`, `hasOtherNpc`) is remembered
as the function, whose calls still read the record live.

**Condition 2 — the exactness is PINNED, not only argued.** `tests/generators/spareHookLineFactsWork.test.js`
"a deep-frozen record and place give the same lines as the unfrozen ones, under both accept
shapes" walks a deep-frozen place (the world law, the roster array and every row) with frozen
pools, over three port kinds, five keys and both `accept` shapes, and gets the unfrozen walk's
lines. ES modules are strict, so a write to anything the facts read THROWS. **Planted once:** a
write of a roster row's `name` inside the loop (`institutions[0].name = String(institutions[0].name)`)
turned it red — `TypeError: Cannot assign to read only property 'name' of object '#<Object>'` —
and the plant was removed (the file restored from its copy; `grep -c PLANT` → 0).

**Condition 3 — `accept`.** Its JSDoc now states that it must be a pure test of the line's text and
must not write the place, its roster or any roster row, and names the two callers that hold today:
`drawCardHooks` (the default `() => true`) and `personHooks.js :: truePersonHooks` (`isTrue`, a
check of the text against `settlementHookFacts` computed before the walk). The frozen pin covers
both shapes.

**Every field the facts read on this path, where it is written, and why not inside the walk.** The
record is the literal `{ institutions, tier }` built inside the call; the option is
`waterKind = place.worldLaw.portKind`. The hook pools on this walk (`NPC_FACTION_LOYALTY`'s pools,
`PERSON_HOOKS_BY_TITLE`, `NPC_HOOK_SIBLINGS`) declare five dimensions, measured: `guardPresence`
(9 rows), `navigable` (4), `magic` (3), `market` (1), `institution` (1).
