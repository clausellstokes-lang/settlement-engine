# FABLE RETROVALIDATION QUEUE (ledger branch — the chair's surface)

**Protocol (ODQ §236, owner-ruled 2026-08-17):** when Fable capacity is
exhausted, the chair and all lanes switch to Opus 5 and work CONTINUES —
but every act performed under an Opus chair is MARKED, and this queue
accumulates what the next Fable session must retroactively validate.

## Marking convention (binding on every Opus-chaired session)
- Every ledger row authored by an Opus chair carries "(chair: Opus 5 —
  Fable-unvalidated)" in its header line.
- Every such row ALSO gets an entry below, stating specifically WHAT
  Fable should re-examine — the judgment-dense parts (rulings, adoptions,
  refusals, aesthetic/absolute-bar verdicts, architecture decisions), not
  the mechanical parts (a CAS whose gate receipt is quoted verbatim needs
  no re-validation; the DECISION to expose might).
- Fable-seat SUBAGENT work completed while Fable capacity existed
  (MF-A1, MF-S1, HF-2/3, the §234 fold — all rows through §235) is
  ALREADY Fable-validated and never enters this queue.
- On regaining Fable: the Fable chair walks this queue TOP TO BOTTOM,
  re-derives each judgment from the receipts (never rubber-stamps),
  records per-row RATIFIED / AMENDED / REVERSED in a ledger sitting,
  and empties the queue. An AMENDED/REVERSED row's downstream
  consequences get the §61-style annex re-verification treatment.
