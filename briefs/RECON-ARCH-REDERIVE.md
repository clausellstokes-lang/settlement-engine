## The experiments (each figure from an executed script whose command and output you quote)
**X1 — the anatomy of the enrichment.** For every key the census classed `onRecord: 'transformed'` (`npcs`, `factions`, `history`, `powerStructure`) and for any other held roster you find transformed: field by field, what does the record hold that the step's output did not (added · renamed · dropped · recomputed)? By which function? For each transformation, MEASURED: is it a pure function of facts the record itself carries (re-derivable FROM a record)? is it IDEMPOTENT (apply it to its own output — identical)? is it INVERTIBLE (can the step-form be recovered from the record-form)?
**X2 — why record-pins fail.** For the failing rows, diff the settlement produced under record-built pins against the record, path by path; attribute each divergent path to the step and the mechanism (double enrichment? a field the step expects and the record lacks? an in-place mutator?). Extend from 9 rows to the 63-row sample: the reproduction rate by tier.
**X3 — candidate seams, measured, not adjudicated.** Using scratch wrappers only, measure the reproduction rate over the 63-row sample for at least these shapes, and any better one you find: (a) EARLY pins of DE-ENRICHED values (your scratch inverse from X1, where one exists); (b) LATE pins — every step runs unpinned, and the held keys are overwritten with the record's values at assembly (or restored after every step that provides or mutates them); (c) early pins + deep-clone + restore-after-step ("pins are final and isolated"); (d) skipping a drawing pass whose whole output is already in the pinned roster (`corruptionPass`). For each: reproduction rate, which paths still diverge, caller-record mutation yes/no, wall-clock per re-derivation.
**X4 — the mutators.** For the 18 `mutates` rows: which steps write THROUGH objects they are handed (so a pin bag that aliases a saved record is corrupted), proven by a before/after deep comparison of a frozen-clone control; does deep-cloning the pins on entry remove every caller-side mutation over the 63 rows, and what does it cost?
**X5 — the held-facts reference graph.** Which record fields reference another held entity, and BY WHAT (display name, positional index, id)? Start from the two rename-surface lists and extend by measurement (search the record of a generated city/metropolis for each NPC's, faction's and institution's name occurring outside its own entry). Output a table: referencing path → referenced entity kind → join key. This is what decides what must re-derive when ONE held fact changes.
**X6 — the root-edit experiments (the design's actual promise).** On a generated town and a city, for each of these single edits applied to the held facts — rename an NPC · change an NPC's role · remove an institution · add an institution from the tier's catalogue · change one faction's power share · seat a different governing faction · change a world fact (terrain, then culture) — run the best seam from X3 and report: which top-level record keys change and how many fields in each; whether any UNEDITED held fact changed (flicker — the failure the design forbids); whether any reference in X5's graph now dangles; whether the change is what a DM would call the consequence of the edit (say what moved in plain words: "food security fell one band; the defense reading gained a river crossing"). Where the pipeline cannot express the edit at all through pins (for instance the record holds a computed fact with no step key), say so with the measurement.
**X7 — multi-producer keys.** For `stress`, `stressTypes`, `generationRepairs`, `isolationSupport`, `economicState`: which production does the record hold, and which pin placement (first producer · last producer · restore-after-every-producer) reproduces it.
